## Decisions

- **Ruby 4.0.7, one dependency: `sqlite3`.** json, optparse, open3 and time are stdlib, and
  the database is a file on disk. There is no Rails and nothing to keep current. The gem
  ships its own SQLite 3.53.2, newer than the system 3.46.1, so WAL behaviour will not drift
  when apt moves.
- **Intervals, not samples.** Thirty seconds of sampling would be 2 880 rows a day to answer
  questions about an event that happens twice. One row per contiguous stretch in one state
  makes the history exact and the report a `SUM`.
- **`ac_online` is tri-state and NULL is the point.** 1 is on AC, 0 is on battery, NULL is
  we were not watching. Two bugs during this build came from violating it, and both made the
  numbers *look better* than reality, which is the direction that matters. Nothing downstream
  is allowed to fold NULL into either side of a ratio.
- **A silence longer than 300 s writes an unknown interval.** If the timer stops for any
  reason, that stretch is unknown rather than an extension of whatever came before. This is
  what makes the tool believable, and it is why `Linger=no` was worth a whole README section.
- **An outage is time on battery. Nothing else.** Not "AC off and the router died". The
  router here is a cellular CPE on a 5G connection that may have its own battery, so losing
  the internet is not proof of losing power. Reachability is stored next to the outage as
  context and is never used as a filter.
- **`net_blackout_seconds` is nil when reachability was never observed.** Reporting the whole
  outage as "internet down" because nothing said otherwise would invent a second outage out
  of the first.
- **Percentages are over observed time only.** The report also prints coverage beside every
  number, because a percentage over 3.4 % of a week, labelled "99.9 % on battery", is
  technically true and practically useless.
- **`backfill` trusts an off-line event and never an on-line one.** The kernel logs the
  adapter at boot, so an on-line line says nothing about the hours after it. Those stretches
  become unknown rather than on-AC.
- **`record` refuses a backwards clock; `seed` is a separate path for the journal.**
  Backfilling is the past by definition, so the guard that protects a live recorder would
  make it impossible. They are different operations and have different invariants.
- **The database lives at `~/.local/share/tinaja-power/power.db`, outside any checkout.**
  Reinstalling or deleting the source must never touch the history.
- **The systemd timer is a plain 30 s `OnUnitActiveSec` with no `Persistent=`.** udev on the
  AC adapter would buy at most the 30 s the timer already costs, and whether this driver even
  emits a change event at runtime is unverified — every `off-line` line in ten days of journal
  was a boot line. `Persistent=` was left off deliberately: replaying a missed run would
  record a state change that happened while nobody was watching.
- **`sqlite3` returns 0 and 1, and 0 is truthy in Ruby.** `net_events` converts at the
  boundary, because a caller writing `if event.has_route` would otherwise get the inverse of
  the answer.
- **MIT and 'Eleazar Meza' in the gemspec**, copied from tinaja-bot. Change if wrong.
- **The shebang must not depend on PATH.** `env -i` with systemd's own PATH is what found the
  bug, so the fix has to survive that test, not just pass in an interactive shell. Two
  options, neither taken yet: point `ExecStart` at the absolute rbenv ruby
  (`/home/zarmeza/.rbenv/versions/4.0.7/bin/ruby`, verified working under the systemd PATH
  with `sqlite3 2.9.6` and a correct `status`), or drop rbenv for the service and install the
  gem into the system Ruby. Absolute path is the smaller change and keeps 4.0.7, which the
  `Data.define` in `Sysfs::Reading` wants. A wrapper script that re-execs the right Ruby is
  the third option and is the most robust if the rbenv version ever moves. **Not decided —
  the user should pick.**

  Installing the gem into the system Ruby was considered and rejected on evidence, not taste:
  `required_ruby_version >= 4.0` is checked by RubyGems at install time, and 3.3.8 is refused
  (verified via `required_ruby_version.satisfied_by?`). It would mean weakening the gemspec to
  `>= 3.2` to get a service onto a Ruby the project does not otherwise target. Note that
  `spec.validate` does *not* enforce this, so it is not a substitute for the real check.
- **`Gemfile.lock` is tracked**, committed 2026-10-11 against the usual gem convention of
  ignoring it. The reasoning: this runs from a systemd timer on one known machine, so the
  thing that matters is that the next `bundle` resolves to the sqlite3 build already proven to
  work, not that the repo is idiomatic. There is no CI and no second platform, so there is
  nothing to gain from allowing drift. If a second platform or CI ever appears, revisit it
  then rather than now.

## Tried and failed

- **`filter_map` silently drops `false`.** `[false, nil, true].filter_map { |x| x }` is
  `[true]`, so `ac_online` returned nil for every *unplugged* reading — the one answer the
  whole tool exists to find. Use `map { }.compact` whenever false is meaningful.
- **An ivar and a method with the same name are not the same thing.** `Sysfs#iface` read
  `@route_fields` directly instead of calling `route_fields`, so it always returned nil. It
  looked intermittent only because a test had called `send(:route_fields)` first, which
  populated the ivar.
- **A private `close(interval, at)` shadowed the public `Store#close`.** Ruby resolves the
  later definition, so `store.close` became an ArgumentError. Renamed to `close_interval`.
- **`until` cannot be a keyword argument name.** `def intervals(since:, until:)` is a
  SyntaxError; the parser reads `until:` as the keyword. Used `before:` instead, which fits
  the half-open interval convention anyway.
- **`bundle lock --update` is not free, on this project.** Run to check the lock was
  reproducible, it added `mini_portile2` and a source-build `sqlite3 (2.9.6)` alongside the
  precompiled `2.9.6-x86_64-linux-gnu`, and filled in CHECKSUMS that the committed lock does
  not have. It resolves and the tests still pass, so it is not broken — but it widens the lock
  to two sqlite3 variants, and the source variant exists precisely to compile SQLite from
  source, which is the thing `.carrot.md` deliberately avoids by shipping a prebuilt gem. The
  committed lock was restored from a backup afterwards. Do not casually re-run it.
- **A `catch(:done)` whose block returns nil makes `|| EXIT_OK` fire on the success path.**
  Replaced with a helper that returns a boolean: true means "help was printed, stop".
- **`--db` declared in two places made OptionParser register it twice.** It is declared once
  in the shared `parse!` now, which also means every command's help mentions it.
- **Backfill through `record` died immediately** with `ClockWentBackwards`, because the
  journal is entirely in the past. That guard is right for a live recorder.
- **`segments` that skipped same-state event pairs left a 2.8-day hole** in the history, so
  the report claimed a 7.1-day window when the truth was 9.9 days. It understated unknown
  time, which is the unsafe direction. Segments must be contiguous and cover the full range.
- **`Format.duration` printed "1w 0d" for 7 days 3 hours.** Integer division after `days / 7`
  dropped the remainder. A report that rounds in its own favour is not worth reading.
- **Minitest `setup` is an instance hook, not a class-level macro.** An `included` block
  calling `base.setup` raises NoMethodError. Each test class wires it up itself.
- **`#!/usr/bin/env ruby` silently picks the wrong Ruby under systemd.** Found 2026-10-11,
  before install, not by a crash but by running the documented install under the timer's
  environment. A user unit gets
  `PATH=~/.local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` — no
  rbenv shims — so `env ruby` resolves to `/usr/bin/ruby`, which is 3.3.8 and has no
  `sqlite3`. Result: `LoadError: cannot load such file -- sqlite3`, every 30 s, into the
  journal and nowhere visible in a terminal. The gemspec's `required_ruby_version >= 4.0` is
  not checked on this path, so it does not fail early either. Verified with
  `env -i PATH=... HOME=$HOME exe/tinaja-power status`. Interactivity hid this: in any
  shell, the rbenv shim wins and the same command succeeds.

```

```

A green timer with a failing service is exactly the failure mode above, and it is invisible
without the second command.

## Open questions

- **Does the kernel log `(off-line)` on a live unplug, or only at boot?** Still unresolved, and
  it decides whether udev is worth adding. Re-checked 2026-10-11: the journal holds exactly
  two ACPI adapter lines since 30 September, `Sep 30 08:37:31` and `Oct 05 01:31:29`, and
  both are boot lines — the first is the same second as the kernel version banner, the second
  is exactly boot -5's start. Boots -1 and 0 contain none at all. So no live-unplug evidence
  either way; the timer stays, udev stays undecided. Settle it by pulling the charger for ten
  seconds with `journalctl -kf` running.
- **The battery is at 39 % of design health** — `charge_full 2609000` against
  `charge_full_design 6669000` µWh, 1309 cycles. During a long outage the laptop will
  probably die, and the tool will correctly record an unknown gap rather than a completed
  outage. Long outages will always look truncated. Nothing to fix; worth not being
  surprised by.
- **Should `backfill` read the journal's boot markers too?** It would let the stretches where
  the machine was demonstrably running be marked observed, which would raise the 3.4 %
  coverage from 30 September onwards. Judged not worth it for a feature already known to be
  marginal, but it is the honest next improvement.
- **The bot has not been rewired.** It still parses sysfs itself in `cogs/lalu.py`, and
  `!lalu` was deliberately left alone so the tool could prove itself first. When that
  happens, the cog should shell out to `tinaja-power status --json` and the parsing should
  move into `lib/tinaja_power/sysfs.rb`.
- **Docker is undecided.** The bot has a `python:3.14-slim` Dockerfile and CI. Calling a Ruby
  tool from inside it means adding a Ruby runtime to a Python image. The cheap middle path
  is a `libsqlite3-0` apt line plus letting the bot read the file — but that gives the bot a
  second writer against a database whose gap logic is the whole point, so it is not
  recommended without thinking harder.
- **No raw samples are kept.** The history is exact intervals, which means there is no way to
  ask "what was the battery doing at 3am during that outage" beyond the level at the moment
  it began. Cheap to add a samples table if that is ever wanted.
